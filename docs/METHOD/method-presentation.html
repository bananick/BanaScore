01 · Principes

La Philosophie

Six principes fondateurs et une hiérarchie de vérité pour guider chaque décision.

📄 Docs-First

Écrire la documentation avant le code. Mettre à jour la doc avec le code. Les docs sont la vérité ; le code est l'implémentation.

🎯 Focus-First

Un seul objectif à la fois. Le mécanisme du taquet empêche de passer au suivant tant que le courant n'est pas terminé.

⚙️ Process-First

Les processus métier sont des citoyens de première classe. Chaque processus a un type de délégation, un niveau de confiance, et des métriques.

🔄 Adaptive

Un standard de travail avec qualité intégrée. Le Core Loop gère la majorité ; les spécialistes interviennent quand leur domaine est touché.

🪶 Lightweight

Pas de processus lourd sauf nécessité. Les gates de qualité sont intégrés au workflow : Pre-Flight, Review Gate, Kill Gate.

📍 Local-First

Tout vit dans le repo. Pas de dashboards externes obligatoires. Les fichiers Markdown sont la source de vérité universelle.

La Pyramide de Vérité

Quand il y a conflit, le niveau supérieur prévaut toujours.

🤖 Agents Engineering

Le METHOD traite les agents IA comme des membres d'équipe avec des rôles définis, des surfaces d'information (ce qu'ils lisent/écrivent), des rituels (quand ils agissent), et des préférences de modèle. Chaque agent a un contrat clair : pas d'ambiguïté sur qui fait quoi, quand, et avec quels fichiers.

🚦 Pre-Flight Gate

Vérifier la clarté avant de commencer. CUJ Precision Gate validé ? Managers synced ? Incertitude < 5% ?

✅ Review Gate

Vera valide chaque tâche après exécution. Modèle haut (Claude Opus 4.6). Résultat : ☑️ (validé) ou ⚠️ (rejeté).

🔐 Kill Gate

Junia vérifie avant de fermer : toutes les tâches ☑️ ? Pas de ⚠️ non traités ? Smoke test OK ? Alors on close.

Arbre de Décision

🔪 Utilisez Cursor quand…
Vous savez exactement quoi changer. Quick fix, refactor précis, exploration rapide, pair programming.
🚀 Utilisez Antigravity quand…
Vous voulez un sprint complet. Planification, exécution multi-tâches, reviews, commits automatisés.
🔪 Cursor excelle pour…
Modifications < 30 min, debugging interactif, refactoring de code existant, prototypage rapide.
🚀 AG excelle pour…
Features complètes, sprints structurés, reviews Vera, consolidation Junia, tâches > 1h.

La Question : Comment coexistent-ils ?

🦢 Swanifly

Orchestration visuelle. Dashboard projet. Exécution multi-agent avec UI riche. Pour les projets complexes multi-sprints.

🚀 Antigravity

Agent autonome dans l'IDE. Contexte METHOD natif. Subagents pour parallélisme. Pour le développement quotidien.

Éditions chirurgicales. Chat rapide. Composer pour multi-fichiers. Pour les modifications précises et immédiates.

💡 Leçons apprises

Les frictions entre outils révèlent les gaps du METHOD. Chaque outil a son contexte optimal. La convergence viendra de l'unification des fichiers projet, pas de l'unification des outils.

10 · Pragmatisme

Hors-Méthode

Quand (et comment) dévier du METHOD. Parce que la rigidité est l'ennemi de la productivité.

Distance par rapport au METHOD
✅ 100% METHOD 🟡 Allégé 🟠 Minimal 🔴 Freestyle

🧪 Prototypage / Hackathon

Pas de sprints formels. Pas de Review Gate. Un fichier FOCUS.md suffit. Validez l'idée d'abord, structurez ensuite.

Distance : Faible

🏚 Code Legacy

Intégrer du code existant sans forcer toute la structure METHOD. Gardez le DoD, ignorez le sprint loop complet.

Distance : Moyenne

🚨 Hotfix Client

Watson intervient directement. Minimal fix → test → deploy. Le bug file documente après coup. Rapidité > processus.

Distance : Élevée

📜 Scripts One-Off

Scripts de migration, outils internes, automation. Pas de i18n, pas de review formelle. Un README suffit.

Distance : Faible

🔬 Features Expérimentales

Feature flags, A/B tests. Suivez le sprint loop mais avec un DoD allégé. Si l'expérience échoue, supprimez sans remords.

Distance : Faible

⚠️ Règle d'or

Même hors-méthode, trois choses restent obligatoires : TypeScript strict (no any), Zod schemas pour Firestore, et un commit descriptif. Le reste est négociable.

12 · Positionnement

METHOD vs Agentic Engineering

Comment le METHOD se positionne face aux méthodologies AI-natives émergentes — notamment l'approche de Peter Steinberger (steipete).

🍌 METHOD v307.a

"Docs are truth; code is implementation"

  • 8 agents actifs nommés avec contrats et rituels (+ 5 dormants)
  • Triple gate : Pre-Flight → Vera → Kill Gate
  • 15 fichiers METHOD synchronisés sur 40 apps
  • Sprints structurés, commits par tâche
  • Pyramide de vérité (METHOD > VISION > CODE)
  • Optimisé pour : qualité reproductible à l'échelle

🦢 Agentic Engineering (Steinberger)

"Architecture over syntax; taste over code"

  • Agents anonymes en parallèle (3-8 en grille tmux)
  • Pas de Review Gate — "Fix Forward"
  • CLAUDE.md minimal comme seule documentation
  • Direct-to-main, centaines de commits/jour
  • Human = architecte + couche de goût (taste layer)
  • Optimisé pour : vélocité maximale, 1 personne

Points de convergence

🤝
Vision Humaine
Les humains fournissent la vision, les agents exécutent
📄
Docs = Interface Agent
La documentation est le contrat entre humain et agents
🏗
Architecture > Code
Le design système prime sur les lignes de code individuelles

Emprunts croisés

✅ Ce que METHOD emprunte

Closed-Loop Execution — Brian fait des boucles write→test→fix autonomes avant le Review Gate. Vera Fast-Track — auto-close des tâches à faible risque (<50 LOC, tests OK, lint clean).

🔄 Ce que Steinberger gagnerait

Review Gate — un seul pass de validation éviterait l'accumulation de dette technique. Mémoire institutionnelle — FOCUS.md éviterait la surcharge cognitive qu'il reconnaît lui-même.

💡 Positionnement

Le METHOD est la bonne approche quand : SaaS multi-tenant, données client, 40 apps, fondateur solo qui a besoin de mémoire institutionnelle. L'approche Steinberger est la bonne quand : un ingénieur expert expédie un outil personnel le plus vite possible. La meilleure stratégie : hybridation — la vélocité de Steinberger entre les gates, la rigueur du METHOD aux gates.
